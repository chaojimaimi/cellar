# Cellar 常见问题（FAQ）

> 真机验收期高频问题的沉淀。安装、更新与卸载类问题先看 [README](../README.md)（图形界面（App）一节）；本文按场景问答展开。

## Q1. 安装后一直停在「等待批准」怎么办？

首启引导第 3 步点击「安装守护进程」后，系统会弹出**系统设置「登录项」授权窗口**。如果当时没有完成批准（例如误点关闭），面板会停在「等待批准」态。

恢复办法：

1. **补批准**：打开 系统设置 → 登录项与扩展（含「后台项目」列表），找到 Cellar 守护进程条目并批准；批准后回到面板会自动继续。
2. **清理残留注册**：若补批准后仍无进展，多半是残留注册记录损坏——在面板 pending 态使用**「移除残留注册」**出口清掉旧记录，再重新点「安装守护进程」走一遍授权。

> 「等待批准」只是卡在系统授权环节，不会碰坏任何已有配置；随时可重试。

## Q2. 「守护进程失联」横幅怎么恢复？

出现该横幅的常见操作是：**替换了 Cellar.app 但没有重装守护进程**——系统注册缓存还指向旧 bundle 路径，daemon 反复启动失败，面板检测到失联。

恢复办法（二选一）：

- **App 路线**：面板 →「卸载守护进程」→ 替换/重装 Cellar.app → 打开 → 面板 →「安装守护进程」。系统注册缓存重置后一次拉起成功。
- **手工路线**：直接 `sudo cellar install`（复制最新二进制 + 重新注册 LaunchDaemon）。这条路线不依赖 App bundle，是**确定性恢复**。

`cellar doctor` 第 9 项可查看守护进程注册态，先确认到底卡在哪一层再动手。

## Q3. 双路线怎么选（App 托管 vs 手工 CLI）？

> ⚠️ **升级必读（0.23.0 混装窗）**：App 与 daemon 必须同批升级——升级 App 后**必须重跑管理员安装命令**（面板「安装守护进程」或 `sudo cellar install`）。旧版 daemon 与新版 App 混装时，旧 daemon 的「自动放电」开关在新 App 中已无 UI 关闭入口（0.23.0 起自动放电退役，见 Q15）；`cellar doctor` 的版本矩阵检查（第 10 项）可协助确认三方版本一致。

| 场景                         | 推荐路线         | 原因                                       |
| ---------------------------- | ---------------- | ------------------------------------------ |
| 普通用户日常使用             | 托管（面板安装） | 随 App 整体安装/卸载，系统设置统一管理     |
| 频繁替换 App 的开发者/测试者 | 手工（CLI 安装） | daemon 与 App bundle 解耦，替换 App 零影响 |
| 托管路线反复 spawn 失败      | 手工（CLI 安装） | 确定性恢复，绕过系统注册缓存问题           |
| 手工路线想回归托管           | 面板迁移指引     | 先清理手工残留，再面板安装                 |

**BTM（后台任务管理）注册记录损坏时**，面板路线的「卸载 → 重装」也不一定能修好系统缓存，此时手工路线（`sudo cellar install`）是唯一确定性出口——它走 launchd 直接注册，不经过 App 的注册缓存。

## Q4. 首次打开被 Gatekeeper 拦截（「App 已损坏」/无法打开）？

App 为 ad-hoc 签名、未公证分发，属预期提示：

1. **主路径**：终端执行 `xattr -cr /Applications/Cellar.app`，然后重新打开。
2. **备选**：系统设置 → 隐私与安全性 →「仍要打开」。

注意：macOS 15 起右击 →「打开」的旁路已被移除，请勿尝试。完整说明见 README「Gatekeeper 引导」。

## Q5. 提示检测到其他充电管理工具怎么办？

首启第 2 步环境检查会扫描本机其他充电管理类软件/守护进程（安装目录与运行进程两级）：

- **精确命中（exact）**：硬阻断安装——必须停用/卸载对应工具后才能继续。
- **疑似命中（generic）**：软警示——确认后可以继续，但运行时仍可能互相干扰。

**为什么必须退出竞品**：充电控制键 `CHTE` 只有一个，两个工具同时写就是「双写者互踩」——A 刚停充，B 又恢复，谁都无法正常执法。Cellar 的写入后回读校验会检测到外部写者并显式告警，但**告警不等于隔离**：请先停用或卸载其他充电管理软件，再安装 Cellar。

## Q6. 「放电到上限」时 USB 设备断电？

会。**放电 = 软件层禁用适配器供电**，整机转由电池供电，Mac 的 USB 端口随之掉电——这是适配器被禁用的物理后果，不是故障。

- 正在写盘的外接硬盘可能丢数据，**放电前请先移除**；合盖外接显示器可能进入睡眠。
- 扩展坞/插线板用户注意：即使外接设备自带供电，经 Mac USB 链路的数据连接也会瞬时中断（设备可能重枚举）；带独立存储的业务操作请避开放电时段。
- 电量降至限充目标后自动恢复适配器供电；想提前结束可在面板取消（守护进程崩溃也会自动恢复充电）。

## Q7. 电池校准（一键校准）须知

校准走「充满 → 静置平衡 → 放电至 10% → 恢复限充」四相，完整一轮约 **6–10 小时**：

- **放电相同样会禁用适配器**：外设瞬时断电的注意事项同 Q6。
- **代价**：完整一轮计一次循环次数（cycle count），属于正常损耗；无需频繁校准。
- **建议睡前启动**：整夜无人值守刚好跑完；全程有通知，可随时在面板取消，取消/中止即安全恢复限充。
- **重启即中止**：重启后校准不会续跑（动作状态机自动中止并恢复限充），这是有意的安全设计。
- **macOS 27 首次可用（0.23.2 起）**：27 上无充电控制键族，校准改经域承载通道执行——充满相把域值临时推到 100（系统充电代理跟随充满）；**静置相不写任何键**（域保持 100 浮充，与 26 的「写停充键」行为不同——满电浮充两小时）；放电相与恢复相照旧经适配器控制。**过夜跑完全程是常态：早晨醒来电量可能低至 10%**（放电相目标）——这是校准的正常结束态，接通电源即自动恢复限充并回充。另外，若曾在系统设置设过原生充电上限后又移除（任务注册残留），0.23.2 起 Cellar 会**绕过该残留直接启动**校准（残留非现行上限，域写 100 已覆写其语义，无需先清理）。

## Q8. 为什么充到上限就停了？「温度暂停」是什么？

**充到上限即停**是滞回机制：CHTE 停充键写入后充电停止，电量自放电至恢复阈值（默认上限 −2%）才重新充电——避免在边界反复启停。这是限充的核心行为，不是故障。

**温度暂停**是充电侧热保护：电池温度 ≥ 暂停阈值（默认 40 °C）自动暂停充电，冷却至恢复点（= 暂停点 − 滞回，默认 < 37 °C）才恢复（滞回防边界抖动）。暂停阈值（35–45 °C）与滞回幅度（1–8 °C）可在 App 通用页「充电热保护」节调整。放电因热终止后**不会热态回充**，等冷却再走正常恢复路径。面板实时温度行可以看到当前温度与状态。

## Q9. 健康度为什么和系统设置不完全一致？

Cellar 读取的是 `AppleSmartBattery` 的原始属性，而系统设置的「电池健康度」是 Apple 经**未公开的平滑算法**处理后的显示值。两者差 1–2% 属正常现象，不表示读数错误；Cellar 面板与 CLI 显示的是同一原始数据源。

## Q10. 如何报告设备兼容性？

1. 运行 `cellar doctor --devices`，复制输出的**单行** `key=value` 设备信息（机型/芯片/macOS/固件/后端/键位/放电能力/执法一致性）。
2. 附在 issue 中，并注明机型/芯片/macOS 版本——收录表见 [docs/DEVICES.md](DEVICES.md)「各机型实测行收录表」。

> 该行是字段白名单生成，不包含序列号等隐私字段；提 issue 时请勿自行附序列号/整机 UUID。

## Q11. 为什么风扇开关打开后显示「本机不支持」？

Apple Silicon 各世代机型对风扇控制的开放程度不同。App 采用**运行时实测验证**：写入目标转速后回读实际转速，确认转速跟随才判定本机支持；验证不通过时诚实停用并显示「本机不支持」，而不是盲写——避免写入无效指令或干扰系统热管理。

另外，部分旧世代机型受系统热管理策略保护，风扇控制键无法直接写入，这类机型同样会显示「本机不支持」。停用仅影响风扇降温这一项，限充与电池监测照常工作。

## Q12. 风扇阈值和充电热暂停是什么关系？

两套**独立配置**，互不影响，且两边都可在 App 通用页配置（风扇阈值在「智能风扇降温」节，热暂停阈值在「充电热保护」节）：

- **风扇阈值**（默认 37 °C）：温度到达后提前提速风扇散热，属于主动降温。
- **充电热暂停**（默认 ≥ 40 °C 暂停充电，恢复点 = 暂停点 − 滞回）：电池充电保护的兜底闸门，与风扇开关无关。

两者是协同而非冲突：风扇降温通常会让充电热暂停更少触发；即使风扇功能未开启或本机不支持，充电热暂停依然独立兜底。

两点值得说明：

- **暂停点上限 45 °C 是有意的 fail-safe 设计**：45 °C 是行业充电窗口的上沿——热保护是兜底闸门，允许把它调得更灵敏（更早保护），但**不允许被配置推高到失效**，也没有任何开关能关闭它（滞回幅度同样被钳制在 1–8 °C）。
- **把热暂停调到低于风扇阈值（例如热暂停 35 °C < 风扇 37 °C）不是故障**：两套配置独立生效，会出现「热先停充、风扇后介入」的时序——温度先过 35 °C 触发热暂停（充电已停），升过 37 °C 风扇才提速降温，冷却到恢复点后充电恢复。这是两套独立配置的正常表现。

## Q13. 充电日程（自动化页）的时段语义是什么？

充电日程（v1.6，默认关闭）按「星期 + 时段」自动切换充电策略，最多 8 条、起止时间 30 分钟步进。理解它的关键是**边沿触发**：

- **只在进窗 / 出窗边界动作**：进入时段 → 快照当时的限充策略（「进窗快照」）并应用条目动作（限充至 N% 或放开充电）；退出时段 → 恢复**进窗时快照**的策略，而不是退出那一刻的现值。
- **时段内手动修改是临时的**：例如进窗前上限 80%、窗口内拖到 75%——18:00 出窗时会自动恢复 80%。想长期改上限，请在控制页或时段外修改。
- **跨午夜时段**：结束时间早于开始时间（如 22:00–07:00）即为跨午夜窗口，编辑器会自动提示；时段横跨零点正常工作。
- **「放开充电」会立即充电**：该动作等于窗口内停用限充（系统默认充电）——如果你正处于限充停充状态，进窗会**立即开始充电直至 100%**，编辑器内有警示文案，配置前请确认这正是你想要的。
- **关总开关立即恢复**：日程总开关关闭时，若正处在某条目窗口内，会**立即**恢复进窗快照并静默——例如夜间窗口（限 75%）里关闭开关，电量会马上开始充回进窗前的上限（如 80%），与下一个出窗边界（如 9:00）无关；这是设计行为（关闭后守护进程不持有任何「日程派生」的限值），不是故障。
- **已知边界（时钟回拨）**：系统时钟被回拨会造成一次「假退出 → 假进入」抖动，引擎按确定性规则在下一拍收敛；睡眠跨窗 / DST 切换日窗口随本地钟面漂移，唤醒后自动补判。

## Q14. 为什么不支持快捷指令（Shortcuts）？

Shortcuts 集成的系统通道是 AppIntents，其运行时**硬性要求 App 携带签名 Team ID**——Cellar 为 ad-hoc 签名（不使用付费开发者账号），实测系统在建立信任连接时直接拒绝（`LNConnectionErrorDomain 1200`），无法以工程手段绕过。项目决定不为此引入付费签名，Shortcuts **集成**（Cellar 内部注册快捷指令）**已终止、不再规划**。

> 注（0.19.20 起，**0.23.1 全链退役**）：macOS 27 的充电编排通道（快捷指令备用 + App 内嵌 set 执行 + 通用页「系统限充执行」节）已**整体退役**——daemon 的限充域通道（topoffprotection 域随写目标，agent 分钟级跟随）自 0.21.3 起覆盖全区间目标，App set 断言链已无职责。已按旧版指引创建过快捷指令的用户：**残留无害**，可保留亦可删除，Cellar 不再读取或执行它；通用页编排节已随之移除（域生效值被 Cellar 覆盖时的提示迁至通用页守护进程节尾行）。**升级纪律**：App 与 daemon 请成对升级——混装窗内旧 App 的「充满一次/恢复限充」为有界退化死面（daemon 前置拒收/恢复走域写，功能以新 App 为准）。

替代路径：

- **定时 / 按星期自动切换上限**：用内置「充电日程」（自动化页，语义见 Q13），覆盖最常见的定时场景。
- **脚本自动化**：`cellar status --json` 输出机器可读状态（`jq` 直读），`sudo cellar set/enable/disable` 走退出码约定——cron、launchd 或任意脚本环境均可驱动。

## Q15. 「自动放电」开关去哪了？（0.23.0 退役说明）

**0.23.0 起自动放电自动机退役**：通用页的「自动放电」开关已移除，电量高于新上限时不再自动放电，只会**停止充电**（电量漂浮在旧上限之上，等待自然自放电回落或你手动干预）。退役依据：0.21.2 收紧模式后自动放电在健康执法态从不触发（实测目标 70、电量 95+ 连日零触发），该功能的实际价值已萎缩至「agent 全盲时的自动介入」——该形态历史上从未出现，而可见面（横幅/通知/doctor）与手动出口一直齐备。

保留的等效能力：

- **手动「放电到上限」按钮**（面板放电区）：一键断开适配器、把电量降到当前上限后自动恢复——想主动压电量时用它，随时可点、不受任何冷却约束；合盖状态拒绝启动、放电中检出合盖自动中止、温度 ≥40°C 与 60% 硬地板自动终止。
- **CHIE 断电保护迟滞**（充电控制页开关，默认关，见 Q18）：限充通道降级时的备用执法通道。
- **调低上限即时生效**：拖动停稳约 0.3 秒后即作为真实策略下发；放电动作进行中滑杆暂不可调（点「取消」结束放电即可恢复调整）——这两条交互不变。

> ⚠️ 混装窗提醒：升级 App 后请重跑管理员安装命令（面板「安装守护进程」或 `sudo cellar install`）——旧 daemon 配 new App 时，旧 daemon 的自动放电开关在 App 中没有关闭入口（见 Q3）。

## Q16. 系统设置的充电上限和 Cellar 是什么关系？（三分支模型）

macOS 27 上系统设置 → 电池 →「充电上限」滑杆与 Cellar 的限充执行之间是**此消彼长**的关系，实测存在三种形态（0.21.3 执法模型对齐的依据）：

1. **系统设置设了具体值（如 80%）** → 系统原生限充主导：充电停在该值，Cellar 的域值执法被它顶掉。适合「只想用系统自带限充」的用户——此时请直接停用 Cellar（面板停用按钮），避免两套执法互相拉锯。
2. **系统设置为 100%（经 API 写入，如 Cellar 执行）** → 机制保持开启，Cellar 的域执法生效——这是 Cellar 正常工作的**前提形态**。**0.22.4 模型 v2 口径**：域文件里的目标值会被系统 agent **直接镜像为有效停充点（含 <80 目标）**——「域执法需要 Cellar 先把系统上限打到 100% 打底」的旧假设已被 2026-10-04 13:32 真机事件证伪（MCL 滞留 100 实际 = 无限制，且会诱发系统 agent 自主把机制再关掉）；因此 0.22.4 起 Cellar 在域承载区间**不再写 100**——恢复链写一次 `max(目标, 80)` 开启垫脚石后即由域值直接执法，系统设置里的滑杆读回值随域值走属预期。
3. **系统设置为 100%（手动在系统设置界面拖到 100%）** → ⚠️ 这不是「关闭限充」，而是**整体关闭了原生限充机制**（实测机制三键同关）——电池会自由充到 100%，Cellar 的域值被无视。

**因此：绝不要在系统设置把上限设成 100% 来「关闭」限充——那是机制关闭位。** 想停用限充请用 Cellar 面板的停用按钮（会正确恢复全开语义）；想配合 Cellar 请把系统设置交给 Cellar 管理（Cellar 滑杆是唯一意图源，读回行会把任何系统设置侧的覆盖显性化）；只想要系统自带限充就在系统设置设一个具体值并停用 Cellar。

若系统设置被外部改成 100%（机制关闭形态），Cellar 会在 30 秒内检测到并自动恢复（通用页出现「系统设置充电上限 100% 已关闭原生限充机制」警示行，`cellar doctor` 第 20 项也会 FAIL 提示）；反复出现说明有东西持续覆写（如 MDM 策略），请在系统设置设一个具体上限。

0.22.1 起 Cellar 对该形态**全自动恢复**；0.22.2 修正恢复通道为**「写开启值」**：检测到机制关闭锁存后，App 经系统 agent 自身的 API 通道写入 `max(目标上限, 80)`——**非 100 值即开启指令**（0.22.1 写 100 被实证不携带开启指令；写 max(目标, 80) 等价于在系统设置把上限拉到该值：目标 ≥80 时一步到位，目标 <80 时先写 80 把机制打开、随后由 Cellar 接管停在上限）。daemon 在重写冷却到期（最长 10 分钟）后重写域值、系统 agent 分钟级跟随停在上限——**端到端最长约 10-12 分钟**（中位约 5-6 分钟）恢复执法，成功后投递「已自动恢复」通知；若恢复写失败，仍会投递手动指引通知兜底（照指引在 Cellar 重新应用上限即可）。期间充电会停在 Cellar 上限附近，不会自由充至 100%。通用页警示块内会同步显示恢复结果行（「已自动重新启用（时刻）」/「自动恢复失败，已转手动指引」），不依赖通知。

**恢复完成的判据（0.22.3 口径）**：「恢复完成」= **域读回持续一致 ∧ 充电行为跟随目标**——两条同时满足才算；「警示行消失 / 锁存释放」只是中间态。域读回需**连续 2 次**一致（且距 daemon 自己上次写入超过 120 秒，防止把自己的重写误读成外部恢复）才解除机制关闭锁存；解除后通道仍以每 10 分钟一次的周期读回盯住域文件（任何静默漂移 ≤10 分钟被重新捕获，30 秒内加速确认）。如果域文件看着正确、但电量长期停在目标之上不回落（≥30 分钟），说明机制可能仍被系统关闭——`cellar doctor` 第 20 项的行为启发附注与 daemon 日志会提示（若为机制关闭形态，通用页横幅亦会亮起）（形态即本节上述「机制关闭位」）。

注意：0.22.2 起 Cellar 首次投递通知前会检查授权态——如果你的安装从未收到过授权请求（早期版本引导流程不触发请求），届时**系统会弹出通知授权请求，请点「允许」**，此后告警与恢复通知才可见；点拒绝则静默停用（功能不受损，面板横幅仍承担告警通道）。

## Q17. 关闭 <80% 限充或卸载前要注意什么？（<80 残留出口）

macOS 27 上 <80% 限充经由系统私有偏好域执法，系统代理会每分钟跟随域值——实测表明**应用无法程序化彻底撤销一次已建立的限充执法**（把特性开关写 0 或删除偏好域都无效，唯一可复现的注销入口是系统设置界面）。因此请按目的选择出口：

- **只想回到 ≥80% 常规执法**：把 Cellar 上限滑回 ≥80% 即可——Cellar 会随写域值并无缝切换，无需其他操作。
- **彻底关闭 <80% 限充**：先在 Cellar 把上限调回 ≥80%（或停用限充管理）。如需同时关闭系统原生限充，请在**系统设置 → 电池**把上限设为一个具体值后再按系统自身方式关闭——**不要用「设为 100%」来关闭**（那是机制关闭位，见 Q16；0.21.3 起 Cellar 会把它当外部覆写自动恢复并提示）。
- **卸载 Cellar 前**：先走面板「卸载守护进程」或 `sudo cellar uninstall`（退出清理会把域值随写回 100 并恢复系统默认充电），再按上一条在系统设置里确认无残留——防止「应用已卸载、系统仍被钉在旧限值」的残留（如守护进程曾异常终止、清理未执行）。`cellar doctor` 的域状态/残留检查项可协助诊断。

## Q18. 「限充执法已降级」横幅是什么？会自己恢复吗？

<80% 执法依赖系统私有偏好域，macOS 更新等原因可能使通道失效。守护进程每次写入后会做行为验证（约 10 分钟观察窗）；连续未生效会自动重申（3 次封顶），仍无效则**诚实降级**：域值随写回落（0.23.0 起回退值 = `max(目标, 80)`——目标 <80 时回退 80%，目标 ≥80 时保持目标值，横幅里显示的就是真实写入值）、面板横幅告知——不会静默失效，你看到的上限就是真实生效的上限。降级期间守护进程**每小时自动重探**，通道恢复即自动回到正常执法；连续 24 小时无违规后违规计数复位。降级稳态下还可手动开启「断电保护（备用）」迟滞通道兜底（充电控制页开关，约 1 循环/天的物理断电执法）。

## Q19. 统计页的耗电数字是怎么算的？准不准？

Cellar 的能耗统计不靠 App 自己采样功率曲线，而是读 **Apple 固件侧的功率累加器**（`PowerTelemetryData` 累加器族，SMC-NOTES §11.7/§11.8 实测定标）：固件持续把系统负载功率积分成能量计数器，Cellar 周期读两次做差分——因此 **App 没开、Mac 合盖睡眠期间产生的耗电也照常记录**（间隙对如实计入），这是与「采样型」功耗历史工具的结构性差异。

精度与口径的诚实边界：

- **估算口径（~10% 系统差）**：差分值 × 定标常数换算（系统通道 K=1.101 / 放电通道 K≈0.825，第一轮定标）与区间积分存在约 10% 系统差——卡片脚注标注「固件累加器估算」，是估算不是计量。
- **复位低估**：固件累加器偶尔复位（计数回退可检测），复位前后的差分对被剔除、脚注缀「复位 N 次」——该时段能量低估，如实标注不做补偿插值。
- **睡眠是否计入**：睡眠期间累加器是否照常积分待观察期实验定谳（SMC-NOTES §11.10 实验②）。无论结论如何，显示的数字都是固件真实记录的能量——差别只在「这段算不算使用耗电」的解释口径。
- **极端情形**：超过 ~80 小时的长间隙（如长假合盖）且中途恰逢累加器复位时，复位不可检测，该期能量按差值低估且无标注（35 天数据保留窗内理论可达）。
- **今日电量区间**：优先显示系统记录的当日电量窗口（标注「系统记录」，其重置时机由系统决定）；系统键缺席时回落为本页采样点的 min/max（标注「采样」）——两种口径都如实标注来源。

## Q20. 系统设置干扰下为什么能自愈？（四层防线叙事）

macOS 27 上系统设置/系统 agent 与 Cellar 共写同一套充电状态，外部干扰（拖动系统滑杆、拖到 100% 关闭机制、MDM 策略等）随时可能发生。Cellar 的自愈不是单一机制，而是**四层防线逐级兜底**：

1. **第一层·域随写幂等重写**：守护进程每 30 秒 tick 检查域文件（系统 agent 跟随的偏好域），发现被外部改写（读回签名不符）就重写目标值——系统 agent 每分钟跟随域值，写回即恢复。单次外部覆写通常在这一层无声化解。
2. **第二层·机制关闭检测与自动恢复**：系统设置把上限拖到 100% 会整体**关闭**原生限充机制（不是设上限，见 Q16）——连续两次覆写签名命中即锁存，App 经系统 agent 自身 API 通道写一次 `max(目标, 80)` 开启值（非 100 值即开启指令）→ daemon 重写域值 → agent 跟随 → 读回持续一致自动解锁，端到端最长约 10-12 分钟（详见 Q16）。
3. **第三层·诚实降级 + 每小时重探**：若通道本身失效（系统更新等原因），重申 3 次封顶后诚实降级（横幅告知真实生效值，见 Q18），每小时自动重探通道，恢复即回归。
4. **第四层·断电保护迟滞（opt-in 兜底）**：降级稳态下可手动开启 CHIE 迟滞——物理断电执法，完全绕过软件通道，系统设置/agent 都无法对抗（约 1 循环/天的成本，详见 Q18）。

设计原则：**上层恢复依赖下层兜底，任何一层失效都有下一层接住**；全程可见（通用页横幅/通知/`cellar doctor` 第 18-20 项），绝不静默。

## Q21. 更新检查会访问网络吗？为什么提示但不自动安装？

**网络行为（0.23.3 起，Sparkle 2 承载）**：更新检查 = 每日至多一次的 appcast 小额只读 GET（`releases/latest/download/appcast.xml`，GitHub 302 跳转至其下载域——完整域名清单见 [SECURITY.md](SECURITY.md)）+ 关于页「检查更新」手动触发。**发现新版后零下载**——Sparkle 弹出标准更新窗（安装 / 跳过此版本 / 稍后提醒），**你点「安装更新」才开始下载**；下载的更新包经 **EdDSA 签名验证**（公钥钉在 App 内，私钥只在发布机钥匙串）验证不过拒绝安装。不发送任何系统信息（`SUSendSystemProfile=false`）。

**为什么不做「无提示的全自动安装」**：两重理由——① 用户控制原则：安装时机由你决定（这正是更新窗三态按钮的语义，「跳过此版本」= 你要的「提示可关闭」）；② 诚实边界：App 为 ad-hoc 签名（无 Developer ID，见 Q14），Sparkle 安装器虽去除自身下载的隔离属性，但无公证形态下的首启体验仍受 Gatekeeper 约束——**从 0.23.4 起**旧版本才会经 appcast 收到新版提示（首版自举空窗），应用内更新替换 App 后 **daemon 仍需重跑一次管理员安装命令**（半自动边界，见 Q3）。EdDSA 验签已解决「下载的确实是作者发布的」这一信任问题——比 0.23.0-0.23.2 的 URL 白名单 + SHA-256 手动核对强一级原语。

## Q22. 「充满一次」会自己结束吗？（0.23.2 自动恢复）

会。**macOS 26 及更早**：充满判定连续两拍成立即自动恢复限充（写停充键），通知 + 面板横幅照发；若 4 小时内未充满则超时自动终止。

**macOS 27（0.23.2 起）**：充满一次以「临时放开充电窗口」执行——充到 100% 后**约 1.5 分钟内自动回落**到你的限充上限（域承载通道写回目标值，全程免手动），窗口最长 **4 小时**兜底超时（未充满也会自动收口）；恢复完成有通知与横幅。健康通道下回落即时；**若限充通道处于降级稳态**（见 Q18），回落受自愈重探约 1 小时的节奏约束——这是降级通道的固有恢复节奏，通道恢复后即回到正常执法。想提前结束随时点「恢复限充」，立即生效。校准与充满一次互相排他（哪个都不能在对方进行时启动）。
